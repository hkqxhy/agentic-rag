# 技术设计亮点与工程取舍

这个项目的重点不是堆叠 Agent 名称，而是把高校新生问答中的时效、来源、隐私和突发访问问题转化为可验证的系统约束。

## 1. 有界 Agent，而非开放式工具循环

LangGraph 状态图只允许 normalize、classify、direct、clarify、rag、verify 这些明确节点。简单问候直接回答，资料不足时进入澄清，校务问题检索后还要经过证据核验。

这种设计牺牲了一部分自由工具探索，换来三项工程收益：

- 每条路径都有确定的退出条件，避免 ReAct 式循环失控；
- route、node trace、confidence 和 grounded 状态可以持久化；
- 路由与证据行为能通过固定测试集回归，而不只依赖人工观感。

## 2. 词法、向量和图关系协同召回

新生问题同时包含“校园卡”“统一身份认证”等专名，以及“密码忘了怎么办”这类口语表达。单一检索器很难兼顾两者。

系统保留 BM25 与字符 n-gram 的精确命中能力，引入 pgvector Dense Retrieval 提高语义泛化，再使用轻量 GraphRAG 补充跨段实体关系。各路结果通过加权 Reciprocal Rank Fusion 合并，避免直接比较不同检索器不可比的原始分数。

Dense Retrieval 提供 off、shadow、hybrid 三档开关。shadow 只记录新旧结果，不改变线上答案；Embedding 或 pgvector 异常时回退词法链路。这使向量能力可以逐步验证和回滚。

## 3. 生成前约束与生成后核验

候选证据会携带来源编号、权威等级、有效期和内容分数。模型提示词要求千问只依据这些证据回答，并使用 `[S1]` 形式引用。

生成结果还要检查引用、URL 和高风险办事渠道是否能被候选资料支持。越界内容可以被截断或触发抽取式降级。资料不足时，系统返回澄清提示，不让模型用常识补齐校务事实。

## 4. API 受理与模型执行解耦

提问接口先把消息和 Agent run 写入 PostgreSQL，再把 run ID 推入 Redis，随后返回 202。独立 Worker 执行检索和模型调用，API 进程不保存会话内存。

Redis 在这里承担四种职责：任务队列、可重放事件流、取消信号和原子限流。PostgreSQL 保存最终业务事实，Redis Stream 保存短期实时事件。SSE 客户端使用游标续接，因此页面刷新不会丢失已经持久化的回答。

## 5. 模型与外部依赖可降级

千问不可用时，系统仍执行检索、质量诊断和证据核验，并以抽取式回答结束本轮。Dense Retrieval 不可用时回退词法检索。健康检查区分 live 和 ready，让容器编排能够识别进程存活与依赖可用两种状态。

降级不是把错误隐藏起来。generation mode、fallback reason、retrieval diagnostics 和 safety filter 都会进入消息元数据，便于定位回答为何变短或切换路径。

## 6. 效果、模型容量和平台容量分开测

项目把测试拆成三个问题：

- Agent 是否选对路由、使用充分证据并生成受支持的引用；
- lexical、dense、hybrid 哪条检索链路真正提高召回；
- 延迟来自千问调用、单 Worker 排队，还是认证、数据库和 API 层。

因此仓库同时保留 pytest 单元与集成测试、版本化评测集、检索消融命令，以及两套 k6 脚本。真实模型压测控制调用次数，平台突发测试使用不调用模型的完整会话旅程，两类数字不会混在一起描述。

## 能力边界

- 当前 GraphRAG 是进程内轻量图增强，不是独立图数据库集群。
- 当前 SSE 传输 Worker 产生的阶段和文本事件，上游模型调用本身仍可能一次性返回完整答案。
- 100 VU 突发测试用于确认正确性和发现瓶颈，不代表单机稳态支持 100 人同时使用。
- 仓库中的知识是脱敏 fixture，正式资料仍需人工审核、发布和维护。

这些边界保留在文档中，方便面试时区分已经实现的系统能力与后续可扩展方向。
