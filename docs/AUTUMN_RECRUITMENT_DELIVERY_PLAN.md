# Agentic RAG 秋招交付与项目价值计划

> 目标：在阿里云 ECS 4C8G 免费试用窗口内完成可部署、可评测、可压测、可演示的 Agentic RAG 项目，并留下即使服务器关闭也能复现和讲清楚的工程证据。

## 1. 项目定位

Agentic RAG 不是“调用一次大模型再拼一个聊天页面”，而是面向高校新生信息碎片化、来源冲突、时效性强和集中访问等真实问题的智能服务系统。

项目价值分成五层：

1. **业务价值**：把分散在迎新网站、通知、手册和 FAQ 中的信息统一检索，回答时给出来源、适用范围和有效期，减少新生反复寻找与人工咨询成本。
2. **Agent 价值**：用可控状态图完成意图识别、问题澄清、检索、证据判断、工具调用、回答和失败降级，而不是不可解释地无限循环调用工具。
3. **RAG 价值**：实现 dense+sparse 混合召回、元数据过滤、Rerank、证据去重、冲突识别、时效治理和可点击引用，并用消融实验证明每一步是否有效。
4. **工程价值**：具备认证、会话、流式响应、异步任务、缓存、限流、熔断、可观测性、备份恢复、CI/CD 和版本化发布，不停留在本地脚本。
5. **验证价值**：对检索、回答、引用、Agent 路径、性能、稳定性和成本分别建立指标，展示真实结果、失败案例和优化过程。

## 2. 秋招版本的完成定义

只有同时满足以下条件才算完成：

- 新前端支持注册登录、新建对话、历史会话、居中输入框、Markdown/引用展示、SSE 流式输出、停止生成和断线恢复；
- LangGraph Agent 的节点、状态、条件边和失败路径都有代码、图和 trace；
- Hybrid RAG、Rerank、元数据/时效过滤和引用闭环可运行；
- 管理员可以上传、校验、发布、回滚知识版本，未来自动同步接口已预留；
- Docker Compose 能在一台新机器上一键部署并健康检查；
- 评测集、评测命令、基线对比和可视化报告可复现；
- k6/Locust 完成 peak、spike、soak、failure 四类测试；
- 备份恢复、索引回滚、模型超时/限流降级至少各演练一次；
- README、架构图、演示视频和面试讲稿中的数据都能追溯到报告。

不把以下内容作为 V1 必做项：Kubernetes、多地域容灾、学校统一身份认证、自动爬取全校网站、自托管 GPU/vLLM、真正服务 100 名新生。它们作为后续演进设计说明即可。

## 3. 实施顺序

### M0：冻结旧版基线

- 保存当前测试集、检索结果、回答质量、延迟和典型失败案例；
- 固定旧版依赖与启动方式；
- 建立 ADR，记录为什么选择 LangGraph、Qdrant、PostgreSQL、Redis、百炼和 Compose；
- 定义实验 ID：代码 commit、数据集、索引、模型、提示词和配置必须共同确定一个结果。

交付物：`baseline.json`、旧版截图、失败案例清单、首批 ADR。

### M1：工程骨架与数据模型

- 拆分 Web、API、Agent、Retrieval、Knowledge、Evaluation 和 Infrastructure 边界；
- 建立普通账号、会话、消息、run、知识文档、知识版本、评测运行和审计日志表；
- 实现配置分层、数据库迁移、结构化日志、trace ID、错误码和健康检查；
- 建立单元测试、静态检查、镜像构建和 Compose。

交付物：可启动空系统、OpenAPI、数据库 ER 图、CI 记录。

### M2：现代 RAG 与知识治理

- 标题/章节感知切分，保留页码、层级、来源、校区、年级、有效期和权限元数据；
- dense+sparse 混合召回，使用 RRF 或加权融合；
- 元数据过滤、候选去重、Rerank、证据压缩和引用定位；
- 对过期、冲突、低权威资料进行降权或阻断；
- 构建上传、影子索引、回归、原子切换和回滚流程；
- 完成 naive dense RAG、hybrid、hybrid+rerank、完整治理版四组消融实验。

交付物：RAG 对比报告、知识 manifest、引用示例、失败分析。

### M3：Agent 与流式对话

- 用 LangGraph 定义 classify、clarify、retrieve、grade、tool、compose、verify、fallback 等节点；
- 对最大步数、工具白名单、超时、Token 预算和外部副作用设置硬边界；
- 对证据不足、问题歧义、资料冲突和模型失败分别设计降级；
- run 状态放入共享存储，SSE 支持心跳、游标、取消和重连；
- 前端完成新建/历史对话、流式消息、引用和错误恢复。

交付物：状态图、trace 截图、可复现的澄清/降级/工具调用案例。

### M4：评测平台

- 从真实校务场景构造 300+ 黄金问题，包含事实、流程、多跳、时间敏感、校区差异、歧义、不可回答和对抗问题；
- 每条数据保存参考答案、支持证据、来源、标签、难度和期望行为；
- 检索指标：Recall@k、MRR、nDCG、过滤正确率；
- 回答指标：正确性、Faithfulness、Answer Relevance、完整性、拒答正确率；
- 引用指标：Citation Precision、Citation Recall、引用定位正确率；
- Agent 指标：路径正确率、工具选择、澄清率、无效循环率、恢复率；
- 系统指标：TTFT、端到端 p50/p95/p99、错误率、吞吐、Token 和单问成本；
- 规则指标由程序计算，LLM-as-a-judge 使用固定 rubric，并抽样人工复核。

交付物：版本化测试集、CLI、JSON/HTML 报告、趋势图、失败案例浏览器。

### M5：云部署、压测和恢复

- 在阿里云 ECS 4C8G 部署完整 Compose；
- 完成 HTTPS、密钥管理、最小权限、安全组、日志轮转和费用告警；
- 从外部负载机执行 peak、spike、72 小时 soak 和 failure 测试；
- 保存 CPU、内存、磁盘、连接、队列、检索、TTFT、错误率和模型调用曲线；
- 演练 PostgreSQL/Qdrant 恢复、知识索引回滚、上一镜像版本回滚；
- 根据实测结果给出 100 用户容量结论和扩容阈值。

交付物：部署手册、压测报告、Grafana/trace 截图、恢复记录、容量结论。

### M6：作品包装

- README 首页用一张图说明业务问题、架构、核心创新和实测结果；
- 录制 3—5 分钟演示：提问、流式响应、引用、历史对话、知识更新、trace、评测和压测报告；
- 准备 10 分钟面试讲解和 3 个深挖主题；
- 删除密钥和个人数据，检查仓库能从零启动；
- 给所有图表标注测试环境、样本量、版本和日期。

交付物：公开仓库、演示视频、简历描述、面试问答卡片。

## 4. 必须保留的证据包

服务器最终可以关闭，但以下内容必须进入仓库或对象存储：

```text
artifacts/
├─ architecture/       # 架构图、Agent 状态图、数据流图
├─ eval/               # 数据集版本、配置、JSON/HTML、消融结果
├─ load-test/          # k6 脚本、摘要、原始指标、资源曲线
├─ traces/             # 匿名化 trace 和典型失败路径
├─ recovery/           # 备份恢复与回滚演练记录
├─ screenshots/        # UI、Grafana、CI/CD、知识管理
└─ demo/               # 视频链接、演示脚本、录制版本
```

大文件可以放 OSS 或 Release，仓库保存校验和、生成命令和下载说明。任何无法复现的截图都只能作为辅助材料，不能作为核心结论。

## 5. 展示指标看板

最终 README 只展示真实测量值，建议采用下面结构：

| 维度 | 指标 | 基线 | 最终 | 说明 |
|---|---|---:|---:|---|
| 检索 | Recall@10 / nDCG@10 | 待测 | 待测 | 同一黄金集消融 |
| 回答 | Faithfulness / 正确性 | 待测 | 待测 | 人工抽检比例一并公开 |
| 引用 | Precision / Recall | 待测 | 待测 | 引用到 chunk/页码 |
| Agent | 路径正确率 / 恢复率 | 待测 | 待测 | 按场景标签分组 |
| 体验 | TTFT p95 / E2E p95 | 待测 | 待测 | 真实百炼网络调用 |
| 容量 | 成功率 / 最大稳定流 | 待测 | 待测 | 4C8G 外部压测 |
| 稳定 | 72h 错误率 / 内存趋势 | 待测 | 待测 | 不隐藏重启和异常 |
| 成本 | Token/问 / 元/千问 | 待测 | 待测 | 模型路由和缓存后 |

`待测` 必须由流水线生成数据替换，不能在实现前填写好看的数字。

## 6. 简历表达模板

在结果尚未测出前，可以写成：

> 设计并重构面向高校新生的生产级 Agentic RAG 助手，基于 LangGraph 构建可控状态图，引入 Hybrid Retrieval、Rerank、时效/权威元数据治理与可追溯引用；使用 FastAPI、PostgreSQL、Redis、Qdrant 和 Docker Compose 部署于阿里云 4C8G 环境，并围绕 100 用户规模建立效果评测、流式并发、故障注入和备份恢复体系。

完成实测后，再把最有区分度的 2—3 个结果补进去：

> 在 N 条多类型黄金集上将 Recall@10 从 A 提升到 B、Faithfulness 从 C 提升到 D；在 4C8G 环境完成 X 条并发流与 72 小时长稳测试，TTFT p95 为 Y，成功率为 Z；通过缓存和模型路由将单问成本降低 W%。

不要写“服务 100 名用户”，除非确实有 100 名真实用户使用。只有压测时写“按 100 用户规模设计并压测验证”。

## 7. 面试叙事

推荐用“问题—决策—证据—取舍”展开：

1. 新生资料为什么难：来源分散、年份/校区差异、冲突与过期；
2. naive RAG 哪里失败：只做向量相似度，召回不稳定，回答没有可验证来源；
3. 为什么使用 LangGraph：流程需要显式状态、条件分支、恢复和预算约束；
4. 为什么使用 Hybrid + Rerank：关键词对专名/编号有效，dense 对语义有效，Rerank 控制最终证据质量；
5. 为什么选择 4C8G + 云端千问：把昂贵推理解耦，以低成本验证完整应用栈；
6. 如何证明不是玩具：评测集、消融实验、外部压测、故障注入、长稳、恢复演练；
7. 为什么首版不用 Kubernetes：100 用户单机资源足够，Compose 更符合成本和复杂度；扩容阈值和演进路线已经设计；
8. 最大失败是什么：展示一个真实失败案例，以及如何通过数据、trace 和实验定位并修复。

面试官真正关心的不是用了多少技术名词，而是你能否解释每个组件解决了什么问题、怎样验证、失败时发生什么、为什么没有选择更复杂的方案。

## 8. 诚实边界

- 目标指标与实测指标分开；
- 模拟用户与真实用户分开；
- 单机容量与高可用分开；
- 云厂商试用成本与长期运行成本分开；
- LLM Judge 分数与人工评价分开；
- “预留接口”与“已完成自动同步”分开；
- 架构设计图与已部署组件分开。

这种边界不会削弱项目，反而能体现工程判断、实验意识和可信度。
